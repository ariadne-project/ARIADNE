## 1. Purpose, terms and precedence

**Stage:** Stage 1 and 2.

### 1.1 Purpose

**Stage:** Stage 1 and 2.

Every run of ARIADNE's proposed pipeline should leave a record of what happened: which files went in, what each agent attempt received and returned, every model request, every check, every answer and every approval. This document proposes that record and the budgets that bound the machine work. It sets out:

- what is kept for each Stage 1 run, where and in which form, which checksums software computes, and for how long everything is kept (section 2);
- what Stage 2 would add on the record side: a record store with revisions, canonical checksums, receipts and attestations (section 3);
- how Stage 1 measures usage, which limits apply in development, how the measurements are planned, and how evaluation caps are set, frozen and applied (section 4);
- what Stage 2 would add on the budget side: reservations, accounts, seats and a spending limit (section 5);
- the external package's reference values, kept only as a Stage 2 appendix (section 6), and the mapping to the register (section 7).

Scientists never handle these records. They exist so that every value, decision and failure can be traced afterwards, and so that the evaluation can report what the agents used.

### 1.2 Terms

**Stage:** Stage 1 and 2.

- **Provenance ledger** ("ledger"): the append-only list of project entries in the [README](../README.md#provenance-ledger): Decisions, Results, Proposals and the like. In this document "ledger" means only this. It holds no run data; where an entry needs run data, it names where the run log keeps it, as the Result entries for containment reports do (D24 A).
- **Run log** (Stage 1): ARIADNE's append-only record of its runs, written only by software (section 2). It consists of the log files of each run folder and batch folder (section 2.2: the run's entries of sections 2.3 and 2.4, the request log, the monitor log and the batch log), the report index (section 2.7), and the stored files that software writes only to record a run or a batch and that those entries name: the binding files ([Runtime, section 10.2](RUNTIME.md#102-the-binding-file)), the binding maps (section 2.3), containment reports, evaluation run records and batch records. Record files, handoffs, packets and the other stored files are named by the run log, with their checksums, but are not part of it. This is the run log in which D13 A keeps software's checksums (section 2.9). It takes the place of the external package's record service, under the name that the [register, section 5](PACKAGE_ADOPTION.md#5-name-table) gives it.
- **Monitor collector** (proposed): the part of the workflow controller's code that receives the observations of the three monitors ([Containment, section 2.2](CONTAINMENT.md#22-components), row Monitors) and writes them to the monitor log (section 2.6); it writes no other file and may run as a process of its own. As part of the workflow controller's code, it is bound by the row Workflow controller of [Containment, section 12.2](CONTAINMENT.md#122-the-runtime-manifest), like the launcher and the runner.
- **Record store** (Stage 2): the run log's proposed Stage 2 successor, which holds revisions, events, receipts and resource events with compare-and-swap commits (sections 3 and 5).
- **Run:** as in [Workflow, section 1.2](WORKFLOW.md#12-terms). Here it also covers evaluation runs, each one item in one condition and one repetition ([Evaluation interfaces, section 10.1](EVALUATION_INTERFACES.md#101-runs-batches-and-attempts)), measurement runs (below), containment suite runs ([Containment, section 1.3](CONTAINMENT.md#13-terms)) and behaviour-variant runs ([Containment, section 7.5](CONTAINMENT.md#75-the-behaviour-variant)); the field `run_kind` tells them apart (section 2.3).
- **Batch:** as in [Evaluation interfaces, section 10.1](EVALUATION_INTERFACES.md#101-runs-batches-and-attempts): the runs that one admission starts, either an evaluation batch or a measurement batch, never both. A batch has its own batch log and batch record (sections 2.2 and 2.3).
- **Measurement run:** a run of a measurement batch: one item in one condition and one repetition, in mode A or B, on a development entry, a variant of one, or a measurement-only size variant, under the development profile. It scores nothing and reads no expected-side file. The measured maxima come only from measurement runs (section 4.8).
- **Stored file:** a file that software stores for a run or a batch, written once and never changed: the input, packets, agent outputs, round snapshots, reports, issue lists, answer files, the originals of assisted entries, human action files, approval statements, final files, binding maps (section 2.3), the attempt folders after their attempts, evaluation run records and batch records.
- **File reference:** how a run-log entry names a stored file: its artifact id ([Handoffs, section 2.1](HANDOFFS.md#21-conventions-for-every-handoff)), its place in the run or batch folder (section 2.2), its SHA-256, its size in bytes and its media type. File references exist in the run log only, never in a record file, handoff or packet.
- **Checksum:** the SHA-256 of a file's exact bytes, written as exactly 64 lowercase hexadecimal characters, matched as a whole string (below), and computed by software (section 2.9).
- **Whole-string grammar:** every identifier and checksum in the run log, the ARIADNE identifiers of [Handoffs, section 2.1](HANDOFFS.md#21-conventions-for-every-handoff) (entry, run, batch, attempt and artifact ids among them) and every checksum, matches its grammar as a whole string: no character before or after it, so no trailing newline, carriage return or whitespace, and no more or fewer characters than the grammar allows. Each grammar keeps its own characters, case and length. Software never trims or rewrites a value to make it match; a value that does not match is refused, never repaired.
- **Request log:** the model gateway's part of the run log, with entries for every request ([Runtime, section 11.3](RUNTIME.md#113-the-request-log); section 2.5).
- **Usage:** the token counts that the provider reports for one request: uncached input, cache writes, cache reads and output, and reasoning where the provider reports it separately (section 4.2).
- **Unknown usage:** a usage count that a forwarded request should have and that is missing or incomplete (section 4.4).
- **Budget profile:** a named, versioned set of limit values under which an attempt runs: the development profile or the evaluation profile (section 4.1).
- **Runaway guard:** as in [Runtime, section 1.2](RUNTIME.md#12-terms). **Capability zero:** as in [Containment, section 11](CONTAINMENT.md#11-capability-zeros). **Evaluation cap:** a limit of the evaluation profile, set from measurements and frozen by a ledger Decision before any test-set run (section 4.9).
- **Measured maximum:** the largest value of a quantity seen in the measurement runs of section 4.8. Token maxima are taken only over requests whose usage is complete; the maxima of requests, wall time, attempts and container resources are taken over all forwarded attempts (section 4.4); a value that a runaway guard cut is never taken as measured (section 4.8, row Guard hits). **Projected maximum:** the largest value that the projection of section 4.8 gives over the 15 to 25 benchmark entries.
- **Trace:** the entries of a run log read in order, as the story of the run. It shows observable steps only (section 2.12).
- **Named person, human action, assisted entry:** as in [Issue format 6](../ISSUE_FORMAT.md#6-human-actions) and [6.3](../ISSUE_FORMAT.md#63-assisted-entry): the person working on a record, normally the scientist, takes the human actions; there is no separate curator role. Entries and texts written before version 1.1 that name the curator keep that name as history.
- **Live pointer, binding, held:** as in [Issue format 2](../ISSUE_FORMAT.md#2-basic-terms) (Live pointer) and [7.1](../ISSUE_FORMAT.md#71-flow) ("Live pointers"). The bindings are kept in the binding map, a run-log file distinct from the binding file of an attempt (section 2.3).
- **Agent attempt, launcher, runner, attempt folder, binding file, model gateway, route record, pipeline stage:** as in [Runtime, section 1.2](RUNTIME.md#12-terms). **Technical failure, attempt result, failure class, technical re-run:** as in [Handoffs, sections 1.2 and 2.13](HANDOFFS.md#213-attempt-result-and-technical-failure).

### 2.5 The request log

**Stage:** Stage 1.

[Runtime, section 11.3](RUNTIME.md#113-the-request-log) says what the gateway logs; this section gives the fields. Their derived schema file is `request-log-entry.schema.json` in [design/specs](specs/README.md#the-files). The gateway writes two entries for each model request: a `request` entry when the request arrives and has been checked, before anything is forwarded, and a `response` entry when the response has ended, was cut, or was closed. A forwarded request without a `response` entry has unknown usage (section 4.4). A refused request gets only a `request` entry.

**Stage:** Stage 1.

### 2.9 Checksums (D13 A)

**Stage:** Stage 1; the last table row, which points to section 3, Stage 2.

Under D13 A, software keeps the checksums it computes in the run log only, no record file, handoff or packet carries a checksum, and the record format stays unchanged ([Issue format 11](../ISSUE_FORMAT.md#11-deliberately-left-out)). The run log is meant as section 1.2 defines it: the log files of each run and batch (section 2.3), the report index (section 2.7), and the stored files that software writes only to record a run or a batch and that those entries name, that is, `binding.json` ([Runtime, section 10.2](RUNTIME.md#102-the-binding-file)), binding maps (section 2.3), containment reports, evaluation run records and batch records ([Evaluation interfaces, sections 10.1 to 10.3](EVALUATION_INTERFACES.md#101-runs-batches-and-attempts)). None of these is a record file, handoff or packet. Outside the run log, checksums appear only where a decided text, the evaluation dataset or the containment suite's fixture store puts them, none of them written during a run: the input's own checksum in its manifest row ([Q1](../OPEN_QUESTIONS.md#q1---which-existing-datasets-should-be-used)); the checksums in the evaluation dataset's lists, that is, the variant list, the item lists, the example manifests and the expected files, none of which is a record file ([Evaluation interfaces, section 3](EVALUATION_INTERFACES.md#3-input-side)); and the schema pin in the register ([register, section 3](PACKAGE_ADOPTION.md#3-precedence-and-pins)); and the fixture-store entries of the containment suite, whose fixtures the runtime manifest binds ([Containment, section 12.2](CONTAINMENT.md#122-the-runtime-manifest), row Fixtures), none of them a record file. The rules:

- A checksum is the SHA-256 of the exact bytes as stored, written as exactly 64 lowercase hexadecimal characters and matched as a whole string (section 1.2, Whole-string grammar): a value with a trailing newline, carriage return or whitespace, or with more or fewer characters, is refused, never trimmed.
- No record file, handoff or packet gets a checksum field. No agent computes, sees or writes a checksum ([Handoffs, section 2.4](HANDOFFS.md#24-input-packets), "Never in any packet").
- Proposed: software computes the checksum of every stored file when it is stored. This includes the list of [Handoffs, section 2.1](HANDOFFS.md#21-conventions-for-every-handoff) (row Checksums) and adds the software-written files, so that a resumed step can confirm that its stored inputs are unchanged.
- A mismatch found by a check is handled as the row says; it is never repaired.

### 2.10 Write-once and append-only rules

**Stage:** Stage 1.

| # | Rule | Stage |
|---|---|---|
| 1 | **Written once.** A stored file is written under a temporary name and then renamed, made read-only, and never changed. A new version is a new file with a new artifact id; the next round gets a new snapshot ([Workflow, section 1.2](WORKFLOW.md#12-terms)) | Stage 1 |
| 2 | **Append-only.** Log entries are never edited or deleted. A mistake is corrected by a `correction` entry that names the entry it corrects; the earlier entry stays. Stage 1 keeps no checksum chain between entries; the gapless sequence numbers show whether an entry is missing in every log file, the report index included (section 2.7) | Stage 1 |
| 3 | **Software writes, nothing in a container does.** Only the workflow controller, the model gateway and the monitor collector, which is part of the workflow controller's code (section 1.2), write log files ([Roles, section 8.2](ROLES.md#82-operations), row 13). Into a run folder, the launcher only moves attempt folders after their attempts (section 2.2); it writes no log file. The runner's facts reach the run log only through `result.json`, which the workflow controller reads once after the container has ended ([Runtime, section 10.3](RUNTIME.md#103-the-sequence), step 8) | Stage 1 |
| 4 | **People through software.** People never write to the run log. | 5 | **Ids, numbers and times by software.** Entry ids, sequence numbers, rounds and times are written by software ([Workflow, section 1.3](WORKFLOW.md#13-ground-rules), rule 3) | Stage 1 |
| 6 | **Record-scoped reads.** A run-log read made for a record's steps ([Roles, section 8.2](ROLES.md#82-operations), row 12) returns the entries of that record and never lists or reads another record. | 8 | **Counters never reset.** Resuming, re-running and starting a new round keep every count (section 4.7) | Stage 1 |
| 9 | **A failed write stops the step.** If an entry or a file cannot be written, the step counts as not done: a technical failure, and the run is suspended ([Workflow, section 4.4.1](WORKFLOW.md#441-what-counts-as-a-technical-failure)) | Stage 1 |

### 2.12 Traces

**Stage:** Stage 1.

A trace is a run log read in order: the `state_change` entries give the path through the states of [Workflow, section 2](WORKFLOW.md#2-stage-1-states), and the entries between them show what each step did. A trace shows observable steps only:

- what software did, with the files it read and wrote, and the result of each check;
- what each agent attempt received (its packet) and returned (its raw output), and how software classified the result;
- every request the gateway forwarded or refused, and what came back;
- what people supplied, and when.

A trace never holds, reconstructs or guesses a model's hidden reasoning. Where a provider returns reasoning text in a response, that text stays inside the stored response body (section 2.11): it is not a trace entry, it is never shown as the reason for a result, and it never enters a packet, a record, an issue or an evidence entry. Reasoning tokens are counted as usage (section 4.2), but their text is not read. The illustrative traces of [Workflow, section 5](WORKFLOW.md#5-traces-stage-1) follow the same rule: they list states and observable steps.

## 4. Budgets, Stage 1

**Stage:** Stage 1.

Stage 1 measures everything and caps little. Under the token-cap decision of 2026-10-19 and D12 A, development runs have no token caps, and usage is always measured at the model gateway; evaluation runs get caps set from those measurements. How each limit is enforced is set out in [Runtime, section 12.3](RUNTIME.md#123-limits).

### 4.1 Budget profiles

**Stage:** Stage 1.

**Rules for profiles** (Stage 1):

1. **Explicit.** Every value is written out; none is left to a default of Hermes, the provider or the library. "Disabled" is a written value, never an omission.
2. **Zero means not allowed.** A zero is never read as unlimited (section 4.5).
3. **In configuration, not in code.** Values live in versioned profile files, so that caps set later from measurements need no design change. A change is a new profile version, recorded in the run log.
4. **Nothing raises a limit from inside.** No request option, prompt text or model output changes a value; gateway rule 7 refuses any other `max_tokens` ([Runtime, section 11.2](RUNTIME.md#112-the-request-shape-rule)).
5. **Not calibrated until measured.** Nothing is calibrated in Stage 1 before the measurements of section 4.8; every value not set from them carries "not calibrated".
6. **No fresh allowance.** A new profile version, a resume or a re-run never resets what has been counted (section 4.7).
7. **Which runs use which profile** (proposed). Pipeline runs and behaviour-variant runs always use the development profile, also after the evaluation caps are frozen. Measurement runs use it too (section 4.8). Runs of evaluation batches use the profile that [Evaluation interfaces, section 10.6](EVALUATION_INTERFACES.md#106-usage-and-budget-profiles) names. So the code `cap_hit` arises only in runs of evaluation batches (section 2.8).

### 4.3 Usage records and totals

**Stage:** Stage 1.

- **The usage record.** The request log is the usage record of every attempt ([Runtime, section 11.3](RUNTIME.md#113-the-request-log)); Hermes's own token counts are kept as diagnostics only.
- **Totals.** Software adds up the forwarded requests' usage per attempt (`attempt_ended`), and per agent step, pipeline stage, agent, round, record and run. The totals go into the `suspended` and `run_ended` entries and into the evaluation run record ([Evaluation interfaces, sections 10.3 and 10.6](EVALUATION_INTERFACES.md#103-fields-of-an-attempt)).
- **Scope.** Totals cover every round, every technical re-run and every resume of a record; nothing is ever subtracted or reset (section 4.7). A restart is a new run, linked to the old one; totals are reported per run and summed per entry ([Workflow, section 4.4.5](WORKFLOW.md#445-ending-a-run)).
- **Flags travel with totals.** A total that includes a request with unknown usage carries that flag and the number of such requests (section 4.4); a total that includes a provisional count is provisional too and is never reported as final.
- **No money limit.** Stage 1 sets no spending limit (section 5.7). Proposed: the measurement Result may give a cost estimate from the provider's published prices on a stated date, labelled as an estimate.

### 4.4 Unknown usage

**Stage:** Stage 1.

Usage is unknown when a forwarded request has no `response` entry, when a stream was cut before its final usage event, when a response that the client abandoned was closed with only part of its usage reported ([Runtime, section 11.3](RUNTIME.md#113-the-request-log)), when the provider returned an error without usage, or when a count the definitions of section 4.2 need is missing. Then:

1. **Flagged, never zero.** The request's `usage_unknown` field names each missing or incomplete category. A missing count is left out, never recorded or added up as zero. A count that the provider reported for an incomplete category is kept beside its flag as provisional: a lower bound, never presented as the request's final count. A run with unknown usage is never reported as having used less.
2. **Carried upward.** The attempt and every total that includes the request carry the flag and the number of affected requests, and such a total is provisional (section 4.3).
3. **Kept out of token cap-setting.** The token maxima (section 4.8) are taken only over requests whose usage is complete; a provisional count never sets or calibrates a token cap. The maxima of requests, wall time and attempts, which a missing usage count does not affect, are taken over all forwarded attempts, so that a long attempt that ended in a cut stream still counts there. The measurement Result reports how many requests were left out of the token maxima, and from which items. Proposed: if a request left out might have been the largest, for example a cut stream after a long output, its item is measured again, so that the maximum does not rest on what happened to be counted. A value that a runaway guard cut is a different case, set out in section 4.8, row Guard hits.
4. **Reasoning not reported** is not unknown output: the output count still includes it (section 4.2). It is recorded as `not_reported` and stated in the measurement Result.

### 4.5 Capability zeros

**Stage:** Stage 1.

Delegation and child agents, recursion, fallback requests, helper requests (titles, compression, background review, plugin model calls), mixture-of-agents calls, tools for any agent, and model requests by deterministic software all stay at zero. They are containment rules, not budgets (D12 A): no count ever reaches them, any count above zero is a containment failure, and no limit value grants a capability. Their tests are CZ-01 to CZ-06 in [Containment, section 11](CONTAINMENT.md#11-capability-zeros).

### 4.7 Rounds and counters

**Stage:** Stage 1.

- **Rounds are counted, not capped.** [Issue format 7.1](../ISSUE_FORMAT.md#71-flow) sets no round cap, and neither does this document ([register, conflict C-11](PACKAGE_ADOPTION.md#7-conflict-register)); limits on rounds, if any, are set later from measurements.

### 4.9 Evaluation caps

**Stage:** Stage 1.

D12 A sets the evaluation caps from measurements, recorded by a ledger Decision and frozen before any test-set run. This is the only place where the formula for them is given; other documents link here.

**The formula** (proposed; decided with the measurement results). For each agent:

| Cap | Value | Rounding | Bound | Stage |
|---|---|---|---|---|
| Output tokens per request (`max_tokens`, reasoning included) | About twice the measured maximum output of one request | Up to the next multiple of 1,024 | Never above the route's documented maximum output | Stage 1 |
| Input tokens per request | About twice the projected maximum input of one request over the 15 to 25 entries | Up to the next multiple of 1,024 | Input cap and output cap together never above the route's context length | Stage 1 |
| Requests per attempt | About twice the measured maximum | Up to a whole number | None | Stage 1 |
| Wall-clock time per attempt | About twice the measured maximum | Up to a whole minute | None | Stage 1 |
| Agent attempts per pipeline stage | About twice the measured maximum | Up to a whole number | None | Stage 1 |

Where twice the measured output maximum would exceed the route's maximum, the cap is the route's maximum, and the measurement Result says so. Where the input cap and the output cap together would exceed the route's context length, the input cap is lowered to the context length minus the output cap, and the measurement Result names the entries whose projected packet then exceeds it; they would stop with code `cap_hit`, or with `packet_too_large` where the packet does not fit the route's context length ([Runtime, section 12.1](RUNTIME.md#121-the-route-record)), in the order of the checks that section 4.10 (row Input tokens) sets out.

**Freezing** (Stage 1):

- The ledger Decision records the evaluation profile's version and every value per agent, the measurement Result it rests on, the versions that were measured (the route record, the Hermes pin, the admitted request templates, which carry Hermes's system text ([Containment, section 12.2](CONTAINMENT.md#122-the-runtime-manifest)), and the prompt, reference-text and example-manifest versions) and the date. It is recorded before any test-set run (D12 A).
- A test-set batch runs only under the frozen evaluation profile ([Evaluation interfaces, section 7.1](EVALUATION_INTERFACES.md#71-admission-proposed), rule 6). Before the freeze, evaluation runs on development items use the development profile and are development runs ([Evaluation interfaces, section 7.1](EVALUATION_INTERFACES.md#71-admission-proposed), rule 5); after it, they run under the evaluation profile ([Evaluation interfaces, section 10.6](EVALUATION_INTERFACES.md#106-usage-and-budget-profiles)). Measurement runs always use the development profile (section 4.8).
- How each frozen cap is enforced is set out in [Runtime, sections 11.4 and 12.3](RUNTIME.md#123-limits); for the input cap, in [Runtime, section 12.3](RUNTIME.md#123-limits), row Input tokens per request.
- Proposed: a change of any value needs new measurements and a new ledger Decision. So does, before a further test-set run, a change of anything the Decision records as measured: a new version of the route record ([Runtime, section 12.1](RUNTIME.md#121-the-route-record)), a new Hermes pin or admitted request template, or a new prompt, reference-text or example-manifest version. Results under different profile versions are reported apart.

### 4.10 Cap hits in evaluation

**Stage:** Stage 1.

Under D12 A, a cap hit under the evaluation profile is a technical failure. Proposed handling, by the classes of [Handoffs, section 2.13](HANDOFFS.md#213-attempt-result-and-technical-failure): each cap hit is handled as the same stop is handled without a cap, so that the one technical re-run of D14 A follows where it follows under the development profile and nowhere else. The `cap_hit` field (sections 2.4 and 2.8) names the cap; where the stop has no class, the code `cap_hit` takes the place that `runaway_guard` has under the development profile.

| Cap reached | How it shows | Class or code | Technical re-run | Stage |
|---|---|---|---|---|
| Output tokens | A response stops at the frozen `max_tokens`, as its logged stop reason shows ([Runtime, section 13.2](RUNTIME.md#132-native-result-classification), row 3 or 8). Under the evaluation profile, every stop at `max_tokens` is a cap hit, because `max_tokens` is the frozen cap; a stop at the context window stays class `truncated`, without `cap_hit` | Class `truncated`; `cap_hit: output_tokens` | One (D14 A) | Stage 1 |
| Requests per attempt | The gateway refuses a request at the frozen cap (gateway rule 8; [Runtime, section 13.2](RUNTIME.md#132-native-result-classification), row 2) | Outcome `technical_failure`, code `cap_hit`, no class; `cap_hit: requests`. This is how the request guard is handled under the development profile (D19 A; [Runtime, section 12.3](RUNTIME.md#123-limits)): a runaway series of repeats would recur | None | Stage 1 |
| Wall-clock time | The launcher stops the container at the frozen guard ([Runtime, section 13.2](RUNTIME.md#132-native-result-classification), row 4), or the runner's watchdog interrupts the call shortly before it and its result says so (row 6; [Runtime, section 5.5](RUNTIME.md#55-during-and-after-the-turn)) | Class `crashed`, as D18 A sets for the guard; `cap_hit: wall_clock` | One (D14 A, D18 A) | Stage 1 |
| Input tokens | Before the attempt, packet preparation finds the packet above the frozen input cap ([Runtime, section 12.3](RUNTIME.md#123-limits), row Input tokens per request). Proposed order of the two size checks, stated here once: the context-length check comes first, and a packet that does not fit the route's context length stops with code `packet_too_large` ([Roles, section 8.7](ROLES.md#87-denial-and-failure-codes)), so that the item is `not_run` in that condition ([Evaluation interfaces, section 10.4](EVALUATION_INTERFACES.md#104-how-runs-and-batches-end)) and no cap is hit; only a packet that fits the context length but exceeds the frozen input cap is a cap hit | Code `cap_hit`, `cap_hit: input_tokens`; no attempt starts and no try is used | None: the same packet would fail again | Stage 1 |
| Attempts per pipeline stage | An attempt would exceed the frozen cap, as one would exceed the attempts-per-stage guard under the development profile | Code `cap_hit`, `cap_hit: attempts`; the attempt does not start | None | Stage 1 |

- **Input reported above the cap.** If the provider reports more input for a forwarded request than the frozen input cap, the attempt's `attempt_ended` entry flags it (`input_above_cap`, section 2.4) and the evaluation reports it; the outcome stands, since the input has already been sent.
- **Counted, not suspended.** An evaluation run counts each cap hit instead of suspending: a hit that has the one technical re-run (output tokens, wall-clock time) goes on to that re-run; a hit without one (requests, input tokens, attempts), or whose re-run also fails, ends the run as `technical_failure`, and the batch goes on ([Workflow, section 1.4](WORKFLOW.md#14-how-evaluation-runs-use-the-workflow); [Evaluation interfaces, section 10.4](EVALUATION_INTERFACES.md#104-how-runs-and-batches-end)). Cap hits are reported per agent, cap and condition, apart from other technical failures, with first-try and final results apart (D14 A).
- **Scores.** How a cap hit enters scores and acceptance belongs to the open acceptance criteria of [Open questions, Q4](../OPEN_QUESTIONS.md#q4---how-should-extraction-and-verification-be-evaluated), item 5; it is not settled here.
- **Never content, never approval.** A cap hit is never an issue, never a finding about the record, and never leads to approval.
- **The development profile.** Runs under the development profile have no caps, measurement runs and evaluation batches on development items before the freeze included; their guards keep the code `runaway_guard`, and the wall-clock stop keeps the class `crashed`, as [Runtime, section 12.3](RUNTIME.md#123-limits) sets out (section 2.8); what a guard hit does to a run of an evaluation or measurement batch is set in [Evaluation interfaces, section 10.4](EVALUATION_INTERFACES.md#104-how-runs-and-batches-end).
