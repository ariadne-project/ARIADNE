## 1. Purpose and how to read this document

**Stage:** Stage 1 and 2.

### 1.1 Purpose

**Stage:** Stage 1 and 2.

ARIADNE's three agents (extraction, verification and inquiry) need a runtime: software that sends the agent's packet to a language model, receives the answer and returns it to ARIADNE. This document proposes how Hermes Agent serves as that runtime in Stage 1. It records:

- why Hermes Agent was chosen (section 2);
- which Hermes release is pinned and how an upgrade works (sections 3 and 13.6);
- what was checked in the Hermes source at that release, and how it compares with the external design package (sections 4 and 9.2);
- the proposed process model: one fresh operating-system process, in its own container, per agent attempt, and what it must switch off (section 5);
- which ways out of the agent ("paths") exist at the release, mapped to the containment tests (section 6);
- the licence note (section 7) and what later phases must re-check (section 8), with the order of the phase P8 implementation (section 8.6);
- the Stage 1 settings, verified at the tag (section 9);
- the attempt sequence from attempt folder to accepted output (section 10);
- the model gateway that holds the provider key (section 11);
- the model route, the admission check and the limits (section 12);
- how results are classified, which Hermes interfaces are used and which are not, runtime independence and the upgrade policy (section 13);
- the decisions D15 to D24 of 2026-10-20 (section 14), the Stage 2 tables (section 15) and a mapping note to the register (section 16).

### 1.2 Terms

**Stage:** Stage 1.

- **Agent attempt:** one run of one agent on one packet. It ends with an output or a technical failure.
- **Launcher:** ARIADNE software that prepares the attempt folder, registers the attempt at the model gateway, starts the attempt's container and stops it at its deadline.
- **Runner:** ARIADNE software inside the container that builds the Hermes agent, makes the one call and writes the result.
- **Attempt folder:** the folder the launcher prepares for one attempt; the only host folder the container sees (section 10.1).
- **Binding file:** `binding.json` in the attempt folder: the ids, round, prompt, route and limits of the attempt, written by software (section 10.2).
- **Container:** the Docker or Podman container in which one attempt runs (decision D10, option A); one per attempt.
- **Home folder:** the folder that Hermes reads its settings, plugins and secrets from, and writes its caches to. Hermes names it with the environment variable `HERMES_HOME`.
- **Model gateway:** the local service that holds the provider key and forwards, counts and logs every model request (the package's "broker"; [register, section 5](PACKAGE_ADOPTION.md#5-name-table)). It runs on the host, outside every container, and is the containers' only network destination (section 11).
- **Gateway token:** a random string, valid only at the model gateway, only for one attempt and only until its deadline (section 11.1).
- **Route record:** the record of the one model route that receives the agents' requests: protocol, dated model, documented maximum output, context length and data-use terms (section 12.1).
- **Runaway guard:** a provisional limit that stops an attempt or a pipeline stage that has gone wrong; marked "not calibrated" (decision D12, option A; section 12.3).
- **Pipeline stage:** one agent's step in one round: the extraction (with all its parts, if it is split; each part is an agent step of its own for the technical re-run, [Workflow, section 4.4.2](WORKFLOW.md#442-the-one-technical-re-run), clarification 1), the verification or the inquiry. "Round" keeps its meaning from [Issue format 2](../ISSUE_FORMAT.md#2-basic-terms).
- **Loop iteration:** one pass of Hermes's agent loop, the unit that `max_iterations` counts. It is not a round.
- **Built-in tools:** tools that ship inside Hermes, such as the terminal, file and web tools.
- **Advertised tools:** the tools whose descriptions the model receives and may call.
- **Registered tools:** the tools Hermes holds handlers for in the process, whether advertised or not.
- **CT-nn:** a containment test row. CT-01 to CT-18 are defined in the [register, section 6](PACKAGE_ADOPTION.md#6-coverage-register); CT-19 to CT-27 are proposed in section 6 of this document. The tests themselves are in [Containment, sections 4 and 5](CONTAINMENT.md#4-path-tests-ct-01-to-ct-18).
- **The package:** design package ARIADNE-AGENT-ARCH-001 v1.2.1, used only through the register.

## 2. Why Hermes Agent

**Stage:** Stage 1.

Hermes Agent is an open-source agent framework from Nous Research, written in Python. It runs a language model in a loop that can call tools, and it can be used as a library inside other software. ARIADNE uses a narrow part of it: one agent object per process and one conversation turn per agent attempt (section 5).

Tillman Heisner chose Hermes Agent as the Stage 1 runtime on 2026-10-19, for three reasons:

1. **Open source under the MIT licence** (section 7). ARIADNE can read the code it relies on, cite exact lines and pin an exact release.
2. **The decision-maker's preference.**
3. **Easy to build on later.** Its plugin interface can carry ARIADNE's read tools when they are added in Stage 2 (decision D6, option A), and its settings cover most of what ARIADNE must switch off (sections 5.3 and 9).

This section documents the runtime choice; the [consolidated ledger record](../README.md#2026-10-29---workflow-and-review-design-consolidated) records documentation consolidation only.

**What the choice does not change.** ARIADNE's formats (packets, agent outputs, issues, run records and the EnzymeML output) stay independent of the runtime. No ARIADNE format carries a Hermes field name. The runner reads Hermes's result and translates it into ARIADNE's run log. Checksums of prompts are taken on ARIADNE's own text, and the text Hermes adds is recorded separately (H-V5.12). Replacing Hermes later would change the runner and this document, not the formats (section 13.5).

**What the choice costs.** The re-check found three properties that ARIADNE's design must work around rather than switch off:

- every Hermes process registers Hermes's built-in tools when it starts, whatever the settings (H-V3.1);
- Hermes adds its own text to the system prompt, including host details (H-V5.12);
- one agent attempt can send more than one model request, and no setting guarantees exactly one (H-V5.5).

So ARIADNE's safeguards rest on the launcher, the model gateway and the container around each attempt (D10 A), not on Hermes settings alone (sections 5, 10 and 11).

**Relation to the package's commit.** The package audited commit 82ef40ab, an untagged commit 135 commits after `v0.21.7`, which itself is 9,957 commits after `v2026.9.24`. The package's Hermes claims were therefore not assumed; each one used here was re-checked at the tag (section 4).

**How an upgrade works.**

1. A newer tag is chosen by the same rule as D5 A: the newest stable tag that is at least two weeks old. A tag chosen in any other way is a new decision by Tillman Heisner.
2. The facts in sections 4 and 9.2 are re-checked at the new tag, at least those marked provisional and those that rest on internal Hermes surfaces (section 8.4), and the links are moved to the new commit.
3. The container image is rebuilt with the new tag and gets a new digest. The full containment test suite ([Containment](CONTAINMENT.md)), including the start-up registry test SU-01 ([Containment, section 3](CONTAINMENT.md#3-start-up-precondition-test-su-01)), and the start-up self-check (section 5.4) are rerun at the new tag, and the gateway's admitted request template is captured again (section 11.2). The new tag is used only after all of them pass and the containment report for the new runtime manifest is VERIFIED ([Containment, section 12](CONTAINMENT.md#12-admission-rule)).
4. The new pin is recorded in this section, and every run log names the pin it ran with. Ledger Result entries follow the one rule of [Containment, section 12.4](CONTAINMENT.md#124-the-admission-check) (D24 A): an entry for the first VERIFIED report at each pin, and for a VERIFIED report that follows a FAILED one, as D32 A reads it.

A tag upgrade that passes the suite needs no new ledger Decision. A new Decision is needed only for a change of runtime, a patch to Hermes or a fork of Hermes (section 13.6).

## 5. Process model

**Stage:** Stage 1. Isolation: one container per agent attempt (D10 A; section 10), with run-time monitors on every attempt (D22 A). Tools: none (D6 A); the runner empties Hermes's tool registry (D15 A), and safe mode keeps plugins, shell hooks and webhooks out (D16 A). All three agents use Hermes's agent loop (D17 B). Model route: one Anthropic Messages route for all three agents (D11 A1; section 12.1). Limits: D12 A, with the provisional values of D19 A and the container limits of D20 A (section 12.3). Tillman Heisner decided these on 2026-10-20; the Stage 1 design documents them ([ledger](../README.md#2026-10-29---workflow-and-review-design-consolidated); [register, section 4.3](PACKAGE_ADOPTION.md#43-decided-by-tillman-heisner-on-2026-10-19-not-yet-in-the-ledger)).

### 5.1 One fresh process per agent attempt

**Stage:** Stage 1.

- The workflow controller starts a **new operating-system process, in a new container, for every agent attempt** (D10 A): each extraction, verification and inquiry attempt, each part of a split extraction ([Handoffs, section 4.3](HANDOFFS.md#43-extraction-in-parts-contingency)) and each technical re-run ([Issue format 7.1](../ISSUE_FORMAT.md#71-flow); D14 A). No process or container runs two attempts.
- Before the container starts, the launcher prepares the **attempt folder** (section 10.1): the read-only packet, prompt and binding file, a fresh home folder copied from a template (section 5.3), an empty, read-only working folder and an output folder. The runner reads the binding before it imports Hermes, because plugin registration happens during import and lasts for the life of the process (H-V2.1).
- The runner builds **one agent**, makes **one** `run_conversation` call, classifies the result (section 13.2), writes it to the output folder, calls `close()` and exits. The launcher then removes the container, and the home folder is archived, read-only, as [Run records, section 2.11](RUN_RECORDS.md#211-retention) sets out (CT-22).

### 5.2 What the re-check changes in the safeguard

**Stage:** Stage 1.

The 2026-10-19 runtime decision says "only ARIADNE's tools". At the tag, Hermes registers its built-in tools in every process that can run an agent, and no setting stops this (H-V3.1, H-V9.3). Any code inside the process can run a registered tool directly (H-V3.3). The runtime decision is therefore documented as an agent that is "offered only ARIADNE's tools" ([ledger](../README.md#2026-10-29---workflow-and-review-design-consolidated)). The proposed wording of the safeguard is:

> Only ARIADNE's tools are advertised to the model and can be called by it; in Stage 1 there are none (D6 A). No code other than ARIADNE's runner runs in the process. Hermes's built-in tools cannot cause effects outside the attempt's container, whose only network destination is the model gateway (D10 A). As defence in depth, the runner also removes them from the registry after the agent is built (H-V3.6; D15 A, section 14).

The model side is covered by Hermes's own name check (H-V3.4, provisional) and by the empty tool list (H-V3.5). The code side is covered by keeping foreign code out (section 14.2) and by the container (section 10).

### 5.4 Start-up self-check

**Stage:** Stage 1.

After building the agent and before any model request, the runner checks the following and does not start the turn if any check fails. The checks on tools are repeated after the turn, because some tools are added per turn (H-V3.5). The runner records a failed item in `result.json`, before the turn as well as after it. If a check repeated after the turn fails, the attempt is void (section 13.2, row 1). A failed check is recorded with code `startup_check_failed` ([Roles, section 8.7](ROLES.md#87-denial-and-failure-codes)); before the turn, no model request is made. An attempt stopped at its wall-clock guard counts as a failed self-check when the gateway had answered the runner's status request (item 8, sent first; section 10.3, step 4) and no model request had reached the gateway, whether the self-check was still running or had finished with the turn not yet at its first request (section 13.2).

1. The effective configuration equals the admitted `config.yaml`, which actually loaded (H-V4.2), including Tool Search `off` (H-V3.7), compression off (H-V5.1), lazy installs off (H-V11.11), the curator, external logins and hook auto-accept off (section 5.3) and the retry values of section 9, because an unreadable value silently becomes the default (H-V11.3). In a containment run under the test-only setting "negative configuration" (section 11.2), the file compared with is the negative `config.yaml` that the binding names; nothing else in this list changes.
2. The loaded plugins equal the admitted set: none (D6 A; H-V1.3, H-V9.7). With `HERMES_SAFE_MODE=1`, no general plugin, shell hook or outbound webhook is registered (D16 A; H-V9.30).
3. The advertised tool list is empty (H-V3.5).
4. Stage 2 only, with the read tools: both ARIADNE tools are registered (H-V2.1, H-V2.2).
5. No MCP toolset is registered (H-V3.2).
6. The imported model-provider modules and the registered tool names are listed in the attempt result (H-V1.3, H-V3.1). After building the agent and before this item, the runner removes every registered tool (D15 A; H-V3.6); this item confirms an empty registry and is repeated after the turn (section 14).
7. The only credential visible to the process is the gateway token (H-V6.5, H-V9.17).
8. The model gateway answers a status request for the attempt's token; this is not a model request (section 11.1).
9. The Anthropic SDK imports from the image, and no package was installed (H-V11.11).

### 5.5 During and after the turn

**Stage:** Stage 1.

- **Deadline.** The runner's watchdog thread calls a hard interrupt shortly before the attempt's wall-clock guard (H-V4.6), and the launcher stops the container at the guard if it has not exited (H-V9.18; section 10.3). Hermes's own run budget is not a deadline (H-V11.6). Output that arrives after the stop is discarded (CT-18; section 10.4). A stop at the guard, whether by the watchdog's interrupt or by the launcher's stop (section 13.2, rows 6 and 4), is class `crashed` (D18 A; section 12.3), unless it counts as a failed start-up self-check (section 5.4), and gets the one technical re-run of D14 A if a request of the attempt was forwarded; otherwise it uses no try (D25 A; section 13.2, attempts with no forwarded request).
- **Monitors.** The three run-time monitors run during every real attempt, as in suite runs; an unexplained record discards the output and suspends the run, or, in a run of an evaluation or measurement batch, stops the run, and the batch stops (D22 A; section 10.3, step 3; [Evaluation interfaces, section 10.4](EVALUATION_INTERFACES.md#104-how-runs-and-batches-end)). They must be ready before the container starts and observe it until it ends: if they are not ready, no container starts, and incomplete monitoring evidence during the attempt makes it void; both have code `monitor_incomplete`, never a containment hit (section 10.3, steps 3, 7 and 8; AD-D06).
- **Result.** Only a normal text exit with a normal stop is candidate output, and only if no response of the attempt stopped at the length limit or ended without a stop reason (a cut stream) that no repeat of the same body followed, whatever Hermes's final exit says (section 13.2, row 3; H-V11.16); everything else is a technical failure for the run log (section 13.2; H-V4.4). Token figures from Hermes are diagnostics (H-V4.5); the model gateway's request log is the usage record (section 11.3; H-V5.5).
- **Cleanup.** `close()`, then process exit; the launcher removes the container, revokes the gateway token and archives the home folder, read-only (H-V4.7, H-V9.22; section 10.3, step 9).

### 5.6 Go or no-go for one process per attempt

**Stage:** Stage 1.

| Question | Finding | Verdict | Stage |
|---|---|---|---|
| Is the attempt binding fixed for the right lifetime? | Plugin registration runs once per process and home, during import (H-V2.1). | Go (verified-static): the process is the right unit of binding. | Stage 1 |
| Are attempts kept apart? | The tool registry is process-wide (H-V2.2). | Go (verified-static). | Stage 1 |
| Can "only ARIADNE's tools registered" be met? | Built-ins register at import whatever the settings (H-V3.1). | No-go as worded; go for the reworded safeguard of section 5.2. | Stage 1 |
| Can the model call anything beyond the admitted tools? | Names are checked against the advertised list before anything runs (H-V3.4); `[]` gives an empty list (H-V3.5); Tool Search must be off once read tools exist (H-V3.7). | Go (H-V3.5 and H-V3.7 verified-static; H-V3.4 provisional, because only part of the agent code was searched). | Stage 1 |
| Can code inside the process run other tools? | Direct dispatch checks nothing (H-V3.3); removal is possible but not a security boundary (H-V3.6). | No-go for settings alone: needs no foreign code in the process, and isolation. | Stage 1 |

**Overall:** go for one fresh operating-system process per agent attempt as the unit of binding, separation, cleanup and stopping. It is not enough on its own as a containment boundary.

**D10, decided.** Option C (a fresh process and an isolated home only) cannot make CT-05 and CT-08 provable, and it leaves CT-21 and CT-23 to settings alone: the built-in tool handlers live inside the process (H-V3.1), the environment probe starts sub-processes by default (H-V9.8), building the agent can make metadata requests (H-V4.9) and import can load secrets (H-V6.5). The facts supported a container or an operating-system sandbox. On 2026-10-20 Tillman Heisner chose option A: one container per agent attempt, Docker or Podman, whose only network destination is a local model gateway that holds the provider key, logs every physical request including retries, and refuses fallback and helper calls. The container also makes several launcher conditions easy to guarantee: no `/etc/hermes`, a clean installation pinned by image digest and a network allow-list. Sections 10 and 11 describe the container and the gateway.

### 5.7 Options that need a decision

**Stage:** Stage 1.

### 8.6 Implementation order (phase P8)

**Stage:** Stage 1.

Decided on 2026-10-27 (AD-D06; [ledger](../README.md#2026-10-29---workflow-and-review-design-consolidated)): when Tillman Heisner asks for phase P8 ([register, section 4.5](PACKAGE_ADOPTION.md#45-phases-of-the-integration-plan)), the implementation first proves two narrow slices. Nothing of this has been built or run.

1. **Fixture-driven lifecycle slice.** The real software steps run on stored draft proposals, reports, question rounds, answers, human actions and approval statements, with no model call and no container: the assembly step, the checks, answers and edits composed on the working copy, evidence consistency, held bindings that block approval, the ending in not approvable, safety under interruption, approval and its invalidation ([Workflow, section 5.5](WORKFLOW.md#55-lifecycle-slice-tests-specified-not-implemented)).
2. **One supported runtime profile.** One host with one container engine of D10 A and the Hermes pin of section 3, with the real launcher, runner, model gateway, monitors and monitor collector, against a scripted upstream: the stub model of [Containment, section 2.1](CONTAINMENT.md#21-overview). It measures the start-up overhead of an attempt (the time the monitors and the collector take to become ready before the container starts, and the time from `attempt_started` through the container start and the gateway's answer to the status request to the first forwarded request), the duration of a suite run, and the noise of each monitor (records per attempt, and the share that the reviewed baseline explains), and the times monitors take to become ready and to confirm the end of observation, from which calibrated monitoring deadlines are proposed for Tillman Heisner's approval, while the slice itself runs under the provisional deadlines he approves before its first attempt (section 10.3, step 3), together with the monitor health tests of [Containment, section 5.3](CONTAINMENT.md#53-monitor-health-tests-mh-01-to-mh-07). Which engine, Docker or Podman, and which host operating system are used is not chosen here; the choice is bound by the isolation profile and the host kernel release of the runtime manifest ([Containment, section 12.2](CONTAINMENT.md#122-the-runtime-manifest)).
3. **The full containment suite**, to a VERIFIED report for the runtime manifest in use, before any live model call ([Containment, section 12](CONTAINMENT.md#12-admission-rule)); then the measurement runs of [Run records, section 4.8](RUN_RECORDS.md#48-measurement-plan).

Both slices are software integration tests. They are not evaluation and not mode C ([Evaluation interfaces, section 2](EVALUATION_INTERFACES.md#2-evaluation-modes)), and they give no scientific authorization. They call no live model, store no containment report that admission can use, never stand in for a VERIFIED report and leave the containment suite as it is. Proposed: to keep it so, the workflow controller of each slice is configured with its own storage location and a fixture copy of the report index, as the admission tests AD-01 to AD-05 are ([Run records, section 2.7](RUN_RECORDS.md#27-containment-reports)); the lifecycle slice passes or fails admission only against that copy, and any suite run, report line, hit line or monitor line of the runtime-profile slice is written there, never to the report index that admission reads; the Hermes decision is not reopened. Their figures come from runs against the stub model: they are not measurement runs and set no cap.

### 10.3 The sequence

**Stage:** Stage 1.

1. **Admission.** Before the attempt, the workflow controller runs the admission check (section 12.2; [Roles, section 8.2](ROLES.md#82-operations), row 14) and applies the attempts-per-stage guard (section 12.3), which under the evaluation profile is the frozen attempts-per-stage cap. Packet preparation runs the checksum checks that [Run records, section 2.3](RUN_RECORDS.md#23-run-log-entries) lists for entry `input_check` before a packet is built ([Handoffs, section 2.3](HANDOFFS.md#23-input-file-record) for the input). It then runs its packet check ([Roles, section 7.2](ROLES.md#72-packet-layout)), its size measurement ([Roles, section 8.1](ROLES.md#81-stage-1-tool-set)) and, under the evaluation profile, the check of the frozen input cap (section 12.3; [Run records, section 4.10](RUN_RECORDS.md#410-cap-hits-in-evaluation)). If any of these checks fails, no folder is prepared and no container starts (codes `not_admitted`, `packet_check_failed`, `packet_too_large` and `runaway_guard`; under the evaluation profile, `cap_hit` for the input cap and for the attempts-per-stage cap; or an `input_check` result `checksum_mismatch` or `wrong_folder`; [Run records, sections 2.3](RUN_RECORDS.md#23-run-log-entries) and [2.8](RUN_RECORDS.md#28-run-log-codes)). For an attempt of a containment run, items 1 to 4 of the admission check apply as [Containment, section 12.4](CONTAINMENT.md#124-the-admission-check) sets out.
2. **Prepare.** The launcher creates the attempt folder in its staging area (section 10.1, "Staging and keeping"), and the workflow controller writes the binding, prompt and packet into it; it then checks the budget profile file against the checksum recorded for the run, and the binding's limit values against the profile, and on a difference no container starts (`input_check` result `checksum_mismatch`; [Run records, section 2.9](RUN_RECORDS.md#29-checksums-d13-a), row Budget profile file). The launcher refuses to go on if the target home folder is not empty, so that nothing placed there in advance, such as a shell-hook approval list, reaches Hermes; no container then starts, the refusal is recorded in the run log, and the run is suspended, or, in a run of an evaluation or measurement batch, stopped, and the batch stops ([Evaluation interfaces, section 10.4](EVALUATION_INTERFACES.md#104-how-runs-and-batches-end)); no try is used ([Workflow, section 4.4.3](WORKFLOW.md#443-suspension); CT-07, CT-23; [Containment, section 2.4](CONTAINMENT.md#24-the-container-d10-a)). The run log records it with code `home_not_empty` ([Roles, section 8.7](ROLES.md#87-denial-and-failure-codes); [Workflow, section 4.4.1](WORKFLOW.md#441-what-counts-as-a-technical-failure)). Otherwise it copies the home template, creates the empty `work` and `output` folders, writes the token and registers the attempt at the model gateway: attempt id, run id, run kind, the run folder for its request log and bodies, token, route, the admitted template for the role prompt (system text and headers; none in capture mode), the checksum of the packet text as Hermes sends it (H-V11.9), `max_tokens`, the request limit (section 12.3), the end time (section 11), in containment runs only, any test-only setting of section 11.2 that applies to the attempt, and, in containment runs only, the attempt's own-canary exemption list (section 11.2, rule 11).
3. **Start.** The launcher starts one container from the pinned image (D10 A), with Docker or Podman. Proposed settings: the mounts of section 10.1 and no others, at the same paths in every attempt; a read-only root file system; a private in-memory `/tmp` and `/dev/shm`; a fixed non-root user with every extra privilege dropped, no privileged mode and a fixed `HOME`; the runner's standard input closed, so that nothing in the container can wait for a person; the environment of section 5.3 and nothing else; one private network on which the model gateway is the only reachable address, with no default route and no outside DNS; and container limits on processor, memory and number of processes (D20 A). Also proposed: the gateway's address on that network is fixed and the same for every attempt; it belongs to the isolation profile, which the runtime manifest binds ([Containment, section 12.2](CONTAINMENT.md#122-the-runtime-manifest)), so the base URL in the admitted `config.yaml` never differs between attempts (section 10.2, `gateway_url`). The values of the container limits are set from the phase P8 measurements and are "not calibrated" until then (D20 A); they are not runaway guards of D12 A. A limit hit ends the attempt as class `crashed`, with the limit named in the run log (D18 A; section 13.2, row 4), and gets the one technical re-run of D14 A if a request of the attempt was forwarded; otherwise it uses no try (D25 A; section 13.2, attempts with no forwarded request). CT-08, CT-17, CT-21, CT-22 and CT-27 test these settings. The three monitors of the containment suite (M1 connections, M2 processes, M3 file events; [Containment, section 5.2](CONTAINMENT.md#52-monitors-on-every-run)) also run on every real attempt (D22 A). Before the launcher starts the container, the monitor collector confirms that M1, M2 and M3 are ready to observe this attempt, and records the time (AD-D06). If a monitor or the collector is not ready within the readiness deadline, no container starts: the launcher revokes the token at the gateway, the run log records code `monitor_incomplete` with the monitors that were not ready, and the run is suspended, or, in a run of an evaluation or measurement batch, stopped, and the batch stops; no try is used. If a monitor or the collector fails, or reports lost events, after the container has started, the launcher stops the container at once (step 7), and the attempt is void with code `monitor_incomplete` (section 13.2, row 1). That is incomplete assurance, not a containment hit, so D27 B does not apply; instead, the execution environment admits no further attempt until a named person records a fix and its monitors pass a readiness check (section 12.2, item 1). Where an unexplained record is also observed, `containment_hit` takes precedence and keeps its consequences. The readiness deadline and the end-of-observation deadline are explicit, finite, positive durations in the isolation profile, and admission requires both (section 12.2, item 1; decided on 2026-10-28, [ledger](../README.md#2026-10-29---workflow-and-review-design-consolidated)). Before the first implementation or calibration attempt, that of a slice of section 8.6 included, Tillman Heisner approves two provisional durations, one for readiness and one for the end of observation, each finite and positive. The isolation profile records them, marked "not calibrated", with his approval, and so do the audit records: the containment report and its run-log entry, and each `admission` entry ([Containment, sections 12.2 to 12.4](CONTAINMENT.md#122-the-runtime-manifest); [Run records, sections 2.3 and 2.7](RUN_RECORDS.md#23-run-log-entries)). This document sets no value, and software never supplies a default. Provisional durations serve only phase P8 development and calibration, the measurement runs included, and the containment testing that this configuration needs; no held-out assessment and no run on researchers' data is admitted under them, and, while point 1 of [register, section 4.4](PACKAGE_ADOPTION.md#44-open-decisions) is open, no pipeline run either ([Containment, section 12.4](CONTAINMENT.md#124-the-admission-check)). The phase P8 measurements (section 8.6) are used to propose calibrated durations, which take effect only when Tillman Heisner approves them; no measurement has been made, and neither the provisional nor the calibrated durations have been approved. The deadlines belong to the runtime manifest, so replacing the provisional durations, like any later change, follows its change and recertification rules ([Containment, section 12.4](CONTAINMENT.md#124-the-admission-check); decided on 2026-10-28, [ledger](../README.md#2026-10-29---workflow-and-review-design-consolidated)). An unexplained monitor record discards the attempt's output and suspends the run, or, in a run of an evaluation or measurement batch, stops the run, and the batch stops (code `containment_hit`, [Roles, section 8.7](ROLES.md#87-denial-and-failure-codes); outcome `void`, section 13.2, row 1); every run under the same runtime manifest is then blocked until the containment suite passes again (D27 B; [Containment, section 12.4](CONTAINMENT.md#124-the-admission-check)). If M3 proves noisy in phase P8, dropping it needs a new decision.
4. **Build and self-check.** The runner reads the binding and the token, imports Hermes and builds one agent with the settings of sections 5.3 and 9 and the role prompt as system prompt, with `HERMES_SAFE_MODE=1` in its environment (D16 A). It then sends the status request of start-up self-check item 8 first (section 5.4), so that the gateway's answer is at hand for item 1 under the test-only setting "negative configuration" (section 11.2), then runs items 1 to 5, removes every registered tool from Hermes's registry (D15 A; H-V3.6), and runs items 6, 7 and 9; item 6 confirms the empty registry. A failed check ends the attempt before any model request (code `startup_check_failed`).
5. **One turn.** The runner calls `run_conversation` once, with the packet as the one user message. Its watchdog thread calls a hard interrupt shortly before the wall-clock guard.
6. **Result.** The runner classifies Hermes's result (section 13.2), writes `result.json` in one step (written to a temporary name, then renamed), calls `close()` and exits: with status 0 when it wrote the file, otherwise with another status.
7. **Stop.** If the container is still running at the wall-clock guard, the launcher stops it; it also stops it at once when the gateway reports a refusal that ends the attempt (section 11.2), and when the monitor collector reports that a monitor failed or lost events, or the workflow controller finds that the collector itself has failed (step 3; [Run records, section 2.6](RUN_RECORDS.md#26-monitor-records); AD-D06). From then on the gateway refuses the attempt's token.
8. **Accept.** After the container has ended, the workflow controller reads `output/` once, in the staging area. It accepts the result only if the container exited with status 0 before the guard, `result.json` names the binding's attempt id and round, the record is still at that round, the gateway's log for the attempt shows at least one forwarded request and no refused one, and the monitors show no unexplained record (D22 A; step 3) and complete evidence: each of M1 to M3 was confirmed ready before the container started and observed through the container's end, with no failure and no lost events reported and the collector working throughout (AD-D06). An empty monitor log alone never shows this. The workflow controller reads `output/` only after the collector has confirmed the end of observation, or once the end-of-observation deadline has passed without that confirmation, which is then recorded as end not observed: the output is not accepted, and the attempt is void with code `monitor_incomplete`, subject to the order of section 13.2, with the environment held. Waiting for the end of observation never extends the attempt's wall-clock allowance and never replaces stopping the container (step 7) or cleaning up (step 9). It then adds the gateway's facts (section 11.3), classifies the attempt (section 13.2) and runs the format check on candidate output only ([Handoffs, section 2.2](HANDOFFS.md#22-format-check-content-checks-and-technical-failures)). Any other case is a technical failure, a void attempt or a failed start-up self-check, which has no outcome (sections 5.4 and 13.2).
9. **Clean up.** The launcher removes the container, once the collector has recorded the end of observation or the end-of-observation deadline has passed, and revokes the token at the gateway; a container whose end was not observed is stopped and removed all the same, and the incomplete evidence stays recorded (AD-D06); it deletes `gateway_token` and the empty `work/` folder and moves the attempt folder from the staging area into the run folder ([Run records, section 2.2](RUN_RECORDS.md#22-where-it-is-kept)). The home is archived, read-only, as [Run records, section 2.11](RUN_RECORDS.md#211-retention) sets out, and the archive is named in the attempt's `attempt_ended` entry (`home_archive`, [Run records, section 2.4](RUN_RECORDS.md#24-attempt-entries); CT-22). The binding, packet and output stay with the run log.

**Test-only launcher variants.** Adopted as labelled exceptions for containment runs only (D21 A); real runs never use them: (a) a negative image built from the same lockfile without the `anthropic` package group (CT-08); (b) `HERMES_DISABLE_LAZY_INSTALLS` left out of the environment (CT-08); (c) other mount paths (CT-24); (d) the shorter wall-clock guard of section 12.3; (e) `HERMES_SAFE_MODE` left out of the environment (CT-04, CT-07, CT-23, CT-26; D16 A). The run log and the containment report label every attempt that used one, and each variant is bound as a suite fixture ([Containment, section 12.2](CONTAINMENT.md#122-the-runtime-manifest)). A suite run that used them can still be VERIFIED ([Containment, section 12.1](CONTAINMENT.md#121-report-status)).

**Fresh context for every agent.** Each attempt starts in its own container from its own packet. The verification agent runs as [Issue format 7.1](../ISSUE_FORMAT.md#71-flow) sets out (round 1 only in Stage 1); its packet is built by software from the input, the assembled draft and the round-1 issues ([Handoffs, section 2.4](HANDOFFS.md#24-input-packets)). No conversation, prompt, examples, memory, files or home of the extraction attempt reach it, because nothing outside its own attempt folder is mounted. The same holds for the inquiry agent and for every technical re-run. Examples come only from reviewed development-set records through the example manifest ([Roles, section 7.6](ROLES.md#76-examples)). Agents never see expected outputs ([Open questions, Q4](../OPEN_QUESTIONS.md#q4---how-should-extraction-and-verification-be-evaluated), item 4): no expected-side file is mounted, so none can reach an attempt. ### 10.4 Stopping, late output and resume

**Stage:** Stage 1; leases, fencing and transactions Stage 2 (section 15).

- **Stopping** an attempt means stopping its container; `close` is hygiene and `interrupt` is not relied on to stop anything (H-V4.6, H-V4.7), although the watchdog's interrupt shortly before the wall-clock guard can end the turn first, and it then counts as a stop at the guard (section 5.5; section 13.2, row 6). Stopping a container cannot recall a request already sent to the provider. The gateway logs that request, and its usage is recorded when the response arrives (section 11.3).
- **Late output.** The workflow controller reads an attempt's output once, after the container has ended. Anything written later, and any result for another attempt id or an older round, is discarded and logged (CT-18). The gateway refuses requests after the attempt's end time and after its token is revoked.
- **Technical failures** are recorded in the run log and handled as [Workflow, section 4.4](WORKFLOW.md#44-technical-failures) sets out. A technical re-run, as [Issue format 7.1](../ISSUE_FORMAT.md#71-flow) allows (detail: D14 A; [Roles, section 7.7](ROLES.md#77-checking-an-output-and-the-technical-re-run)), is a new attempt with a new folder, container and token.
- **Resume** starts again at the last safe step of [Workflow, section 4.4.4](WORKFLOW.md#444-resume): the counters are kept, and every agent attempt runs in a fresh container.
- **Not in Stage 1:** leases, fencing generations, atomic transactions and execution seats (section 15). Command deduplication with idempotency keys is Stage 2, if ever ([Issue format 11](../ISSUE_FORMAT.md#11-deliberately-left-out)).

## 11. The model gateway

**Stage:** Stage 1, as a light form of the Stage 2 broker (section 15).

### 11.1 What it holds and forwards

**Stage:** Stage 1.

- **Place.** ARIADNE software (written in phase P8) that runs on the host, outside every container. It is the only address the attempt network can reach (D10 A).
- **Key.** It alone holds the provider key (D10 A) for the one route (D11 A1). The key never enters a container, a packet, the run log or an attempt folder.
- **Token.** Each attempt gets its own random token. The token is valid only at the gateway, only for that attempt and only until the attempt's end time, and it is revoked when the attempt ends or a refusal ends it (section 11.2). It is useless at the provider.
- **Forwarding.** For each request it accepts, the gateway sends exactly one request to the provider endpoint of the route. It forwards the body unchanged and only the admitted headers (section 11.2, rule 12), with its own authentication in place of the token. It never retries, never switches model, provider or endpoint, and never changes the body.
- **Streaming.** Hermes streams its requests by default (H-V11.10). The gateway relays a streamed response as it arrives, without buffering it, and never sends keep-alive frames of its own: an empty frame would switch Hermes to non-streaming calls, whose timeouts can cut a long answer (GR-13, [Containment, section 4.21](CONTAINMENT.md#421-gr-01-to-gr-13---gateway-rules-and-the-refusal-answer)). A response that is not streamed is returned unchanged.
- **Status.** It answers the runner's status request (section 5.4), the workflow controller's question at admission (section 10.3, step 1) whether its upstream is the stub model or the recorded route ([Containment, section 12.4](CONTAINMENT.md#124-the-admission-check)), and the launcher's same question at registration (section 10.3, "Test-only launcher variants"), without contacting the provider.

### 11.2 The request-shape rule

**Stage:** Stage 1.

Every request is checked before it is forwarded. A request that fails a rule is refused and logged, never forwarded.

**The admitted template.** It is captured in the baseline run of SU-01 ([Containment, section 3.1](CONTAINMENT.md#31-what-is-recorded)), with the gateway in capture mode ("Test-only settings", below) and the stub model as upstream, once for each role-prompt version. ### 11.3 The request log

**Stage:** Stage 1.

For every request the gateway records: the attempt id; a sequence number; the request class, which is **first** (the attempt's first request), **retry** (the same body as an earlier request of the attempt) or **continuation** (it extends the attempt's conversation, such as a continuation after a length stop or a cut stream, a nudge after an empty answer, or an error turn after a refused tool call), or **unclassifiable**, with every refused request marked as refused, together with every rule it fails, so that section 13.2 applies its first matching row (a request that fails rules 7 and 9 makes the attempt void); in containment runs, the test-only setting in force (section 11.2), if any; the times sent and answered; the result of the rules (forwarded, or refused with every rule it fails); the checksum and size of the body; the forwarded headers without their authentication values (neither the gateway token nor the provider key is ever logged; sections 10.1 and 11.1); the model and `max_tokens`; the provider's status; the stop reason, or that the response ended without one (a cut stream, rule 9); the usage the provider reports (input, output and cache tokens); and the served model and the provider's request id where the provider reports them. For a streamed response, the stop reason and usage are read from the stream's events (H-V11.10). A response that the client abandons before any stop reason, such as a stream that Hermes cuts at its stale timeout and then sends again (H-V11.10; [chat_completion_helpers.py L3579-3604](https://github.com/NousResearch/hermes-agent/blob/f97608f178d1ffeca59860195ab7da295f7c8e5f/agent/chat_completion_helpers.py#L3579-L3604)), is logged as a cut stream (rule 9): the gateway closes the request upstream and records the usage that the stream reported up to then. The status request of section 5.4 is answered locally and is not logged as a model request; the gateway writes, for each attempt, a `status` entry only when it answered it ([Run records, section 2.5](RUN_RECORDS.md#25-the-request-log)), and the attempt's `attempt_ended` entry copies that time (field `status_answered_at`, [Run records, section 2.4](RUN_RECORDS.md#24-attempt-entries)), so that the class of a stop at the guard before the first request can be checked from the log.

**Unclassifiable requests.** A request has the class first, retry or continuation whenever its definition fits, refused or not. The class **unclassifiable** is allowed only for a refused request that fits none of the three and that carries its refusal reason, that is, every rule it fails: for example a later request of an attempt whose body is the JSON array `[]` instead of one JSON object, which is neither the attempt's first request, nor a repeat of an earlier body, nor an extension of its conversation (it fails rule 1). An unclassifiable request is never forwarded; a forwarded request with this class is an error of the log. It is counted as a refused request and against the request guard or the frozen request cap (rule 8), like every other request, and every count of requests by class has a place for it ([Run records, section 2.5](RUN_RECORDS.md#25-the-request-log)). The class never stands in for validation: a malformed request is refused under the rule it fails, never relabelled as a continuation to fit a class, and the rules of section 11.2 are applied to it unchanged.

**Incomplete usage.** Usage counts that the provider reported are kept even when they are incomplete, such as the output tokens that a cut stream reported before it ended (rule 9): the count is recorded, and its category is named in the entry's `usage_unknown` list, which marks the count as provisional, never as the request's final usage ([Run records, sections 2.5](RUN_RECORDS.md#25-the-request-log) and [4.4](RUN_RECORDS.md#44-unknown-usage)). A count that the provider did not report is never recorded as zero: it is left out and its category is named in `usage_unknown`. The flags carry over to every total that includes the request (attempt, step, run and batch), so that a total with an incomplete or missing count is itself marked incomplete in that category. Provisional and missing counts are never used to calibrate the evaluation caps of section 11.4 ([Run records, section 4.9](RUN_RECORDS.md#49-evaluation-caps)).

The log lies outside every container. It is the usage record of the attempt ([Handoffs, section 2.13](HANDOFFS.md#213-attempt-result-and-technical-failure), `forwarded_requests` and usage); Hermes's own counters are diagnostics (H-V4.5).

**Bodies.** In containment runs, that is, while the gateway's upstream is the stub model, the gateway keeps every request and response body in full: the suite searches them for canaries and compares them with the admitted template ([Containment, section 2.2](CONTAINMENT.md#22-components), request capture), and CT-14 matches the gateway's request classes with the stub model's own log, request by request ([Containment, section 4.14](CONTAINMENT.md#414-ct-14---retries-inside-the-provider-library)). In containment runs the gateway also keeps every request's incoming headers, with authentication values masked; SU-01 records their names in its reviewed baseline, and CT-24 compares every later request with it. This confirms the full header set that the SDK sends and that the gateway token is sent as an API key (H-V11.8, H-V11.13; section 8.2). In real runs, request and response bodies are kept as [Run records, section 2.11](RUN_RECORDS.md#211-retention) says.

What happens when a guard or cap is hit (Stage 1):

- **Wall-clock guard.** D12 A settles that this guard exists, and D19 A sets its provisional value. Under D18 A ([Handoffs, section 2.13](HANDOFFS.md#213-attempt-result-and-technical-failure); [Workflow, section 4.4.2](WORKFLOW.md#442-the-one-technical-re-run), clarification 2), a stop at the guard is class `crashed` (a stop that counts as a failed start-up self-check excepted, section 5.4) and gets the one technical re-run of D14 A if a request of the attempt was forwarded; otherwise it uses no try (D25 A; section 13.2, attempts with no forwarded request); the run log names the cause. The code `runaway_guard` is not used for this stop.
- **Container limit and cut stream.** Under D18 A, a container-limit hit (D20 A) and a cut stream that no repeat of the same body followed, including one that Hermes abandons at its stale timeout (section 11.3), are also class `crashed`; each gets the one technical re-run of D14 A if a request of the attempt was forwarded; otherwise it uses no try (D25 A; section 13.2, attempts with no forwarded request); the run log names the cause, and for a limit hit the limit (section 13.2, rows 3 and 4).
- **Attempts-per-stage guard.** An attempt that would exceed the guard does not start; code `runaway_guard`, and the run is suspended ([Roles, section 8.7](ROLES.md#87-denial-and-failure-codes)). In a run of an evaluation or measurement batch, the run ends as `technical_failure` instead and the batch goes on ([Evaluation interfaces, section 10.4](EVALUATION_INTERFACES.md#104-how-runs-and-batches-end)).
- **Request guard (D19 A).** A refusal under gateway rule 8 in development: code `runaway_guard`, outcome `technical_failure`, no technical re-run, and the run is suspended; the gateway revokes the token and the launcher stops the container (section 11.2). In a run of an evaluation or measurement batch, the run ends as `technical_failure` instead and the batch goes on ([Evaluation interfaces, section 10.4](EVALUATION_INTERFACES.md#104-how-runs-and-batches-end)).
- **Evaluation.** A hit of any frozen cap is a technical failure (D12 A). Evaluation runs count and report it instead of suspending ([Workflow, section 1.4](WORKFLOW.md#14-how-evaluation-runs-use-the-workflow)). Their handling is set out in [Run records, sections 4.9](RUN_RECORDS.md#49-evaluation-caps) and [4.10](RUN_RECORDS.md#410-cap-hits-in-evaluation): a request-cap hit is outcome `technical_failure`, code `cap_hit`, with no technical re-run.
- **Alignment.** [Roles, section 8.7](ROLES.md#87-denial-and-failure-codes), [Handoffs, section 2.13](HANDOFFS.md#213-attempt-result-and-technical-failure) and Workflow, sections [4.4.1](WORKFLOW.md#441-what-counts-as-a-technical-failure), [4.4.2](WORKFLOW.md#442-the-one-technical-re-run) and [4.4.6](WORKFLOW.md#446-limits), follow this section.

Further points (Stage 1):

- Usage is always measured at the gateway. The guard values are the provisional values of D19 A, all "not calibrated"; they give way to the frozen evaluation caps before evaluation.
- Hermes's own limits are not hard bounds: `max_iterations` counts loop iterations, not requests (H-V4.8); `max_tokens` applies to one request (H-V10.1); the run budget is no deadline (H-V11.6). The bounds that hold are the gateway's count and the container stop.
- The evaluation caps, the ledger Decision that records them and the run-log fields are in [Run records, sections 2.4](RUN_RECORDS.md#24-attempt-entries) and [4.9](RUN_RECORDS.md#49-evaluation-caps).

### 13.5 Runtime independence

**Stage:** Stage 1 and 2.

- ARIADNE's formats (packets, agent outputs, issues, questions, answers, run records, the EnzymeML record, its evidence file and its not-mapped report) carry no Hermes name or field (section 2).

- Replacing Hermes would change the runner, the container image, sections 2 to 9 and 13.1 of this document and the Hermes-specific containment rows, and it needs a new ledger Decision (section 13.6).
